# معماری پرشین پدل

سندی فنی از ساختار پروژه، شمای پایگاه داده، جریان‌های کاربری و تصمیم‌های
طراحی. مخاطب این سند توسعه‌دهنده‌ای است که می‌خواهد پروژه را نگه‌داری یا
گسترش دهد.

---

## ۱. انتخاب فناوری

| لایه | فناوری | دلیل انتخاب |
|---|---|---|
| فرانت‌اند | Next.js 15 (App Router) + React 19 + TypeScript | رندر سمت سرور برای بارگذاری سریع روی موبایل ایران، یک پایگاه کد برای UI و API |
| استایل | Tailwind CSS 3 | سیستم طراحی توکنی، خروجی CSS کوچک، پشتیبانی کامل RTL |
| پایگاه داده | PostgreSQL | تراکنش‌های اتمیک و قفل ردیف — الزامی برای کیف پول و جلوگیری از رزرو تکراری |
| ORM | Prisma 6 | شمای نوع‌دار، مهاجرت‌های نسخه‌بندی‌شده، تراکنش‌های تعاملی |
| احراز هویت | پیاده‌سازی اختصاصی (jose + bcryptjs) | نیاز به ترکیب «نام کاربری/رمز» با «تأیید موبایل» که کتابخانه‌های آماده آن را پوشش نمی‌دهند |
| PWA | Service Worker دست‌نویس + Web App Manifest | کنترل دقیق راهبرد کش؛ داده‌ی مالی هرگز کش نمی‌شود |

**چرا Next.js و نه یک SPA + بک‌اند جدا؟** رزرو زمین و کیف پول به داده‌ی تازه و
اعتبارسنجی سمت سرور نیاز دارند. با Server Component‌ها صفحه با داده‌ی آماده
می‌رسد و رفت‌وبرگشت اضافی حذف می‌شود؛ ضمن اینکه استقرار و نگه‌داری یک سرویس
به‌جای دو سرویس برای یک باشگاه ساده‌تر است.

## ۳. شمای پایگاه داده

### کاربران و احراز هویت

```
User ─1:1─ Profile        نام، عکس، سطح، امتیاز کش‌شده
     ─1:1─ Wallet         موجودی به ریال
     ─1:N─ Session        نشست‌های فعال (قابل ابطال)
     ─1:N─ PhoneVerification   کدهای تأیید موبایل
```

شماره‌ی موبایل روی `User` و یکتاست؛ پس از تأیید، `phoneVerifiedAt` پر می‌شود و
تغییر آن فقط از مسیر تأیید مجدد یا توسط مدیر ممکن است.

سطح بازیکن (`Profile.level`) از نوع `PlayerLevel` با دوازده مقدار
`A+ … D−` است و همراه با `levelUpdatedBy` و `levelUpdatedAt` نگه‌داری می‌شود.

### مالی

```
Wallet ─1:N─ WalletTransaction   دفتر کل: مبلغ، مانده‌ی قبل، مانده‌ی بعد
Payment ─1:N─ WalletTransaction  تراکنش درگاه
Profile ←──── PointsTransaction  دفتر کل امتیاز
```

**اصل طراحی:** موجودی روی `Wallet.balance` و `Profile.points` صرفاً مقدار
کش‌شده برای خواندن سریع است؛ **منبع حقیقت، ردیف‌های دفتر کل‌اند.** هر تغییر
همزمان مانده را به‌روز و یک ردیف دفتر کل با `balanceBefore` و `balanceAfter`
ثبت می‌کند، پس همیشه قابل بازرسی و بازسازی است.

### زمین‌ها و رزرو

```
Court ─1:N─ CourtPricingRule   قیمت بازه‌ای (ساعت، روز هفته، اولویت)
      ─1:N─ CourtBlackout      بازه‌های مسدود
      ─1:N─ Booking ─1:N─ BookingSlot
                    ─1:1─ BookingCancellation
```

هیچ ثابتی برای «سه زمین» در کد وجود ندارد؛ مدیر می‌تواند زمین اضافه کند و
مدت سانس، ساعات کاری، حداکثر سانس پیوسته و افق رزرو هر زمین را جداگانه
تنظیم کند.

### تورنومنت

```
Tournament ─1:1─ TournamentLevelRule     قانون ترکیب سطح
           ─1:N─ TournamentPointsRule    امتیاز هر رتبه
           ─1:N─ TournamentCourt
           ─1:N─ TournamentGroup
           ─1:N─ TournamentTeam ─1:N─ TeamMember
           ─1:N─ TournamentMatch
           ─1:N─ TournamentStanding
           ─1:N─ TournamentResult
           ─1:N─ PartnerRequest
           ─1:1─ TournamentDraft ─1:N─ DraftPick
```

## ۴. تصمیم‌های کلیدی

### ۴.۱ جلوگیری از رزرو هم‌زمان (Double Booking)

مسئله: دو کاربر در یک لحظه یک سانس را می‌گیرند.

راه‌حل: هر سانس یک ردیف در `BookingSlot` با محدودیت یکتای
**`@@unique([courtId, startsAt])`** است. کل عملیات درون یک تراکنش انجام می‌شود:

```
BEGIN
  ایجاد Booking
  درج BookingSlot  ← دومین نفر اینجا با خطای یکتایی متوقف می‌شود
  کسر از کیف پول با قفل ردیف
COMMIT
```

اگر درج شکست بخورد، **تمام تراکنش برگردانده می‌شود** — نه رزروی می‌ماند و نه
مبلغی کسر می‌شود. بازنده پیام فارسی روشنی می‌گیرد و فهرست ساعات تازه می‌شود.

> این رفتار با پنج درخواست هم‌زمان روی یک سانس آزمایش شده است: دقیقاً یک برنده،
> یک ردیف سانس، و هیچ کسر وجهی برای بازندگان.

### ۴.۲ اتمیک بودن عملیات مالی

`mutateWallet` همیشه ردیف کیف پول را با `SELECT … FOR UPDATE` قفل می‌کند، پس
دو عملیات هم‌زمان روی یک کیف پول سریالی می‌شوند و «خرج دوباره» ممکن نیست.

هر عملیات می‌تواند یک `referenceKey` یکتا داشته باشد؛ اگر همان کلید قبلاً ثبت
شده باشد، عملیات بدون تغییر موجودی برمی‌گردد. این ویژگی تضمین می‌کند:

- فراخوانی چندباره‌ی بازگشت از درگاه، کیف پول را دوبار شارژ نمی‌کند.
- اجرای دوباره‌ی «پایان تورنومنت»، امتیاز تکراری نمی‌دهد.

### ۴.۳ قیمت‌گذاری سمت سرور

قیمت هرگز از کلاینت پذیرفته نمی‌شود. `priceForSlot` برای هر سانس، قوانین فعال
زمین را غربال می‌کند (بازه‌ی ساعت، روز هفته، بازه‌ی تاریخی) و قانون با بالاترین
اولویت — و در تساوی، باریک‌ترین بازه — برنده می‌شود. در نبود قانون، قیمت پایه‌ی
زمین اعمال می‌گردد.

### ۴.۴ تاریخ و منطقه‌ی زمانی

همه‌ی زمان‌ها در پایگاه داده **UTC** ذخیره می‌شوند. «روز» در اپلیکیشن یعنی روز
تقویمی به وقت باشگاه (`APP_TIMEZONE`). تبدیل‌ها در `datetime.ts` با `Intl` انجام
می‌شود، نه با اختلاف ثابت — پس تغییر احتمالی قوانین ساعت رسمی مشکلی ایجاد نمی‌کند.

تبدیل شمسی ↔ میلادی در `jalali.ts` بدون وابستگی خارجی پیاده‌سازی شده است.

### ۴.۵ انتزاع درگاه پرداخت

```ts
interface PaymentGateway {
  init(input):   Promise<{ providerRef, redirectUrl }>
  verify(input): Promise<{ success, verifyRef, … }>
  extractRef(callbackParams): string | null
}
```

زرین‌پال، زیبال و نکست‌پی پیاده‌سازی شده‌اند و یک درگاه آزمایشی برای توسعه وجود
دارد. افزودن درگاه تازه = یک کلاس جدید + یک سطر در `registry`.

جریان شارژ:

```
کاربر مبلغ را انتخاب می‌کند
  → رکورد Payment با وضعیت INITIATED ساخته می‌شود
  → هدایت به درگاه
  → بازگشت به /api/payments/callback
  → تأیید سمت سرور نزد درگاه (مبلغ تأییدشده با مبلغ درخواستی مقایسه می‌شود)
  → افزایش کیف پول با referenceKey = payment:<id>
```

موجودی هرگز پیش از تأیید سرور تغییر نمی‌کند.

### ۴.۶ قوانین سطح تورنومنت

چهار حالت پشتیبانی می‌شود:

| نوع | رفتار |
|---|---|
| `FREE` | هر ترکیبی مجاز است |
| `EXACT` | سطح هر جایگاه باید در فهرست سطوح آن جایگاه باشد |
| `RANGE` | سطح هر جایگاه باید در بازه‌ی [قوی‌ترین..ضعیف‌ترین] سطوح تعیین‌شده باشد |
| `COMBINATION` | ترکیب باید در فهرست ترکیب‌های مجاز باشد |

با روشن بودن `orderInsensitive`، جای دو بازیکن هم بررسی می‌شود و در صورت نیاز
جایگاه‌ها هنگام ساخت تیم جابه‌جا می‌شوند.

بررسی **دو بار** انجام می‌گیرد: هنگام ارسال درخواست پارتنری و دوباره هنگام
پذیرش — چون ممکن است مدیر در این فاصله سطح بازیکنی را تغییر داده باشد.

### ۴.۷ زمان‌بندی مسابقات

- **لیگ:** الگوریتم چرخشی Round-Robin؛ در تعداد فرد یک تیم مجازی استراحت
  می‌گیرد. رفت‌وبرگشت اختیاری است.
- **گروهی + حذفی:** تیم‌ها به‌صورت مارپیچ بین گروه‌ها پخش می‌شوند تا توازن حفظ
  شود؛ سپس اسکلت براکت از فینال به عقب ساخته می‌شود تا هر مسابقه بداند برنده‌اش
  به کدام مسابقه می‌رود (`nextMatchId` / `nextMatchSlot`).
- اندازه‌ی براکت از تعداد صعودکنندگان محاسبه می‌شود و مراحل (یک‌هشتم، یک‌چهارم،
  نیمه‌نهایی، فینال) خودکار تعیین می‌گردند.
- صعودکنندگان با سیدبندی استاندارد (صدرنشین گروه مقابل نایب‌قهرمان گروه دیگر)
  در براکت قرار می‌گیرند.

### ۴.۸ جدول رده‌بندی

جدول هرگز به‌صورت افزایشی به‌روزرسانی نمی‌شود؛ پس از هر نتیجه **کاملاً از روی
نتایج ثبت‌شده بازسازی می‌گردد**. این کار جدول را در برابر ویرایش یا حذف نتایج
مقاوم می‌کند.

ترتیب: امتیاز ← تفاضل ست ← ست‌های برده ← تفاضل گیم ← گیم‌های برده.

### ۴.۹ اعطای خودکار امتیاز

با «پایان تورنومنت»:

1. رتبه‌ی نهایی محاسبه می‌شود (لیگ: از جدول؛ حذفی: فینال، رده‌بندی، سپس مرحله‌ی
   حذف‌شدن و در نهایت جدول گروهی).
2. برای هر رتبه، اگر مدیر قانون امتیازی تعریف کرده باشد، امتیاز به **هر بازیکنِ**
   آن تیم اضافه می‌شود.
3. هر اعطا با `referenceKey` یکتا ثبت می‌شود، پس اجرای دوباره امتیاز تکراری
   نمی‌دهد.
4. برای هر بازیکن یک اعلان ساخته می‌شود.

تعداد رتبه‌های امتیازآور و مقدار هر کدام کاملاً دلخواه است.

## ۵. جریان‌های کاربری

### ثبت‌نام

```
فرم (نام، نام کاربری، رمز، موبایل)
  → یکتایی نام کاربری و شماره بررسی می‌شود
  → رمز هش می‌شود و همراه اطلاعات در PhoneVerification نگه داشته می‌شود
  → کد یک‌بارمصرف ارسال می‌شود
  → تأیید کد
  → User + Profile + Wallet در یک تراکنش ساخته می‌شوند
  → نشست صادر می‌شود
```

حساب کاربری **فقط پس از تأیید موبایل** ساخته می‌شود، پس رکورد نیمه‌کاره باقی نمی‌ماند.

### رزرو

```
انتخاب تاریخ (تقویم شمسی) → انتخاب زمین → مشاهده‌ی ساعات
  → انتخاب یک یا چند سانس پیوسته
  → مشاهده‌ی ریز قیمت و مبلغ نهایی
  → تأیید → کسر از کیف پول + ثبت رزرو (تراکنش اتمیک)
  → اعلان تأیید رزرو
```

### ثبت‌نام تورنومنت

```
بازیکن ۱ پارتنر را انتخاب می‌کند
  → قانون سطح بررسی می‌شود
  → درخواست ارسال و اعلان ساخته می‌شود
  → بازیکن ۲ می‌پذیرد یا رد می‌کند
       رد   → بازیکن ۱ می‌تواند پارتنر دیگری انتخاب کند
       تأیید → تیم ساخته می‌شود + هزینه کسر می‌شود (یک‌جا یا تقسیم‌شده)
```

## ۷. نکات نگه‌داری

- **افزودن مهاجرت:** `npx prisma migrate dev --name <توضیح>`
- **بازسازی موجودی امتیاز** پس از اصلاح دستی: تابع `recalculatePoints`
- **پاک‌سازی محدودیت‌های نرخ منقضی:** تابع `purgeExpiredRateLimits` (مناسب برای cron)
- **راست‌به‌چپ:** هرگاه دو مقدار عددی را با جداکننده کنار هم می‌گذارید، از
  `<Dot />` یا `iso()` استفاده کنید؛ جداکننده‌های خنثی مانند «·» در الگوریتم
  دوجهته‌ی یونیکد باعث چسبیدن اعداد دو طرف به یکدیگر می‌شوند.
- **ارقام فارسی:** پیام‌های سمت سرور نیز باید از `toFaDigits` استفاده کنند.
